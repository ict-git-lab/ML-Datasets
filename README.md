# Телеметрія стабільності API-ендпоінтів

Файл `Dataset.csv` — зрізи стану API-ендпоінтів під різним навантаженням. Один рядок відповідає одному спостереженню: скільки ресурсів зайняв ендпоінт, як швидко і з якими помилками відповів, яким методом і протоколом прийшов запит, і в якому режимі він при цьому перебував.

Датасет зібрано для задачі оцінки стабільності ендпоінта при пікових навантаженнях: відрізнити штатну роботу і керований пік від втрати стабільності.

## Файл

| | |
|---|---|
| Файл | `Dataset.csv` |
| Рядків | 933, разом із заголовком |
| Стовпців | 8 |
| Пропуски | немає |

Після вилучення дублікатів залишається 928 унікальних спостережень: `Normal` — 303, `High_Load` — 312, `Anomaly_Attack` — 313.

## Стовпці

| Стовпець | Тип | Що означає |
|---|---|---|
| `CPU_Utilization_Pct` | float | Завантаження процесора, % |
| `RAM_Usage_GB` | float | Використання оперативної пам’яті, ГБ |
| `Response_Latency_ms` | float | Латентність відповіді, мс |
| `Error_Rate_Per_Min` | int | Кількість помилок за хвилину |
| `Request_Method` | категорія | `GET`, `POST`, `PUT`, `DELETE` |
| `Protocol_Type` | категорія | `HTTP/1.1`, `HTTP/2`, `gRPC` |
| `Status_Code_Class` | int | Числовий код режиму: 0, 1 або 2 |
| `Status_Name` | категорія | Назва режиму. Цільова змінна |

`Status_Code_Class` не є окремим вимірюванням. Він повторює мітку:

| `Status_Code_Class` | `Status_Name` | Сенс |
|---|---|---|
| 0 | `Normal` | Штатний режим |
| 1 | `High_Load` | Пікове навантаження, ендпоінт ще керований |
| 2 | `Anomaly_Attack` | Втрата стабільності |

У ознаки цей стовпець брати не слід: модель, яка його бачить, просто читає відповідь.

## Розподіл класів

Класи майже зрівноважені. Для бінарної постановки «втрата стабільності / решта» позитивним класом логічно брати `Anomaly_Attack` (313 рядків, 33,5 %), а `Normal` і `High_Load` лишати негативним класом: пік саме по собі ще не є аварією.

## Діапазони телеметрії

Мінімум і максимум на унікальних рядках:

| Ознака | `Normal` | `High_Load` | `Anomaly_Attack` |
|---|---|---|---|
| CPU, % | 15,85–33,34 | 62,82–94,47 | 89,55–100,00 |
| RAM, ГБ | 2,39–5,84 | 7,85–16,20 | 24,65–31,91 |
| Латентність, мс | 25,2–63,1 | 181,6–612,1 | 785,0–1780,3 |
| Помилки за хвилину | 0–3 | 0–10 | 14–35 |

RAM і латентність між трьома класами не перетинаються. Частота помилок відділяє аномалію від решти (мінімум аномалії 14, максимум інших класів 10); норма і пік на ній перетинаються. CPU відділяє норму від навантажених станів; між піком і аномалією є вузький перетин близько 90–94 %.

Через це мітка відновлюється простим правилом без помилок на унікальних рядках:

1. якщо помилок за хвилину не менше 14 — `Anomaly_Attack`;
2. інакше якщо CPU не менше 50 % — `High_Load`;
3. інакше — `Normal`.

Латентність або RAM поодинці також розділяють усі три класи. Модель із якістю, близькою до 1, на цих даних не є свідченням складного узагальнення: класи в телеметрії вже розведені.

Числові ознаки сильно пов’язані між собою (кореляція Пірсона RAM з латентністю і латентності з частотою помилок вища за 0,96). Для наївного Байєса це порушення умови незалежності, але на рішення воно майже не впливає, бо кожної осі окремо достатньо.
